### 跨仓库真实连接

已实测：无源码目录中的独立 PHAR → 本机 HTTP Core → Unix socket Updater。Core 使用临时 SQLite，Updater 使用真实接纳与操作管理代码、只支持备份的测试执行器。

- 显式权限登录，读取实际能力，创建动作计划。
- 操作已接纳后注入一次 HTTP 响应丢失。
- 保留同一请求 ID，不提供第二份密码或动态码，再次执行 CLI 命令只查询收据。
- 等待完成，退出并重新登录，再次取得原操作收据。
- 观测到操作 POST **1 次**、测试备份执行 **1 次**。
- 另一次直接 Core/socket 验证中，移走可重建操作投影并重启 Updater，仍从权威记录取得同一收据，执行次数保持 **1**。

以上证明连接、接纳和续接合同。测试执行器没有调用 Docker、真实数据库备份或外部渠道。

## 独立复核

已完成各阶段规格及质量复核，修复包括：恢复阶段历史压缩后的边界丢失、Redis 隔离目录持久化、旧容器重启窗口、旧 Core 只读入口隐式写入、Web 授权新鲜度、CLI 密码空格保持、失效草稿清理兼容、分发协议下限被在线演练降级。

Updater C 最后复核的两个问题：

1. 较旧 v2 待恢复收据可能覆盖之后成功的主机恢复，并错误记录成功，需要持久的跨入口先后顺序。
2. 目录创建后的父目录同步失败，重试可能跳过已有目录的父级同步，需要在重试中补齐持久化屏障。

两项均已通过独立故障探针复现。修复增加跨入口持久顺序记录，并逐级补齐已有目录及父级的同步。后续复核又确认并修复了“投影早于权威目录同步”的中断窗口：原探针会在备份从未派发时调用 Resume/Verify，修复后部署调用为零。独立质量复核、规格复核和最终全量回归均已通过。

真实 Docker CI 还发现两处旧夹具与新恢复合同不一致。已补充合法的临时实例身份，以及实际运行并读取恢复状态挂载的 PHP 检查容器；生产恢复路径继续完整执行。重跑全部通过，测试修复已经独立审查。

## 当前阻塞及边界

恢复对账的两张新表和“证据未通过即禁止解封”的全局门禁，遭自动审批拒绝；按隔离源码与临时测试库限定重试后仍被拒绝。拒绝理由是该全局执行门禁需要更明确授权。已向维护者提交具体变更说明并询问，仅此依赖工作暂停。现有恢复结果继续明确为 `held`，不会将后台工作报告为已恢复。

即使该门禁获准，非空恢复任务仍需各业务提供永久防重放依据和明确的新执行记录。只读核验和空集合证明不能代替这部分实现。

本轮未部署到现有本地后台或生产环境，未安装全局 Skill/CLI，未推送或发起公开发行。主题发布能力继续关闭。正式配套发行仍要求原生 Linux amd64/arm64 完整演练及对应签名候选证据。
